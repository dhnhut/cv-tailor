**Sprint goal:** A merge to `main` deploys the hello stack to a real `dev` account through GitHub OIDC. Every environment has its own account, SSO access, a budget alarm, and baseline guardrails. The MVP scope is decided.

**Dates:** 2026-09-29 to 2026-10-01 (planned: 2026-09-29 to 2026-10-05)

**Status:** Done

## Scope

- AWS Organization with separate `dev`, `stag`, and `prod` accounts, plus a shared `log-archive` account
- Human access through IAM Identity Center (SSO), with no long-lived access keys
- Baseline guardrails: service control policies (SCPs) and an organization CloudTrail trail that delivers to the log archive
- CDK stages per environment, CDK bootstrap, and a GitHub OIDC deploy role in each account
- Automatic deploy of `dev` on every merge to `main`
- AWS Budgets alarms for each environment (`AGENTS.md` §8)
- Coverage gates at the 80% target (`AGENTS.md` §9)
- First operations runbooks
- The MVP scope decision, which feeds the Sprint 2 backlog

The region stays a single region, `us-east-1` ([ADR-0002](../adr/0002-aws-region.md)). No feature code in this sprint.

## Target Account Structure

```text
Management account (billing, Organizations, IAM Identity Center, org trail definition; no workloads)
└── Root                         ← baseline SCP (applies to every member account)
    ├── Security (OU)            ← log-protection SCP
    │   └── log-archive          (org CloudTrail S3 bucket; shared by all projects)
    └── Workloads (OU)
        ├── NonProd (OU)
        │   ├── cv-tailor-dev
        │   └── cv-tailor-stag
        └── Prod (OU)            ← stricter prod SCPs later
            └── cv-tailor-prod
```

**Why this structure:**

- **OUs group accounts by policy, not by environment or project.** `dev` and `stag` share the same guardrails, so they share `NonProd`. `Prod` exists so stricter SCPs can apply to `prod` later without touching `dev` and `stag`.
- **One account per environment** gives a hard boundary for permissions, quotas, and cost. A mistake in `dev` can't touch `prod`, and each account's bill is its environment's cost.
- **The account is the project boundary.** The Organization can host other projects later: their accounts (`<project>-<env>`) go into the same `NonProd` and `Prod` OUs and inherit the same guardrails.
- **The management account holds no workloads.** SCPs don't apply to the management account, so anything deployed there would sit outside the guardrails.
- **A shared log archive account** keeps the audit logs out of the management account, the most powerful account in the Organization. One trail serves every project.
- **IAM Identity Center** gives short-lived credentials (`aws sso login`) for humans. **GitHub OIDC** gives short-lived credentials for CI. No AWS access keys are stored anywhere.
- **Not Control Tower.** It adds a landing zone, extra accounts, and AWS Config costs that aren't needed at this size. ADR-0004 records this.

### S1-05 details: SCP design

- **Region deny** uses the `aws:RequestedRegion` condition with a `NotAction` list for global services (IAM, Organizations, STS, CloudFront, Budgets, Route 53, Support, Cost Explorer, and similar). The exact list comes from the AWS example SCP and is recorded in ADR-0004.
- **Bedrock cross-region inference:** `us.` and `global.` inference profiles are called in `us-east-1` but can run the request in other regions. The region deny must not block those calls. Bedrock inference outside `us-east-1` is allowed only when the request uses a `us.` profile (following the AWS example SCP for cross-region inference) or a `global.` profile (following the Bedrock documentation for global cross-region inference), so no list of destination regions has to be maintained.
- **Test before attaching to `prod`:** attach to `NonProd` first, verify, then attach to Root.
- **Fewest policies:** statements are merged into one baseline policy, because AWS allows at most 5 SCPs per target, including `FullAWSAccess`.

### S1-07 details: OIDC trust model

```text
GitHub Actions job (environment: dev)
  └─ OIDC token (sub = repo:dhnhut@5567608/cv-tailor@1386961484:environment:dev)
      └─ sts:AssumeRoleWithWebIdentity → GithubDeployRole (dev account)
          └─ sts:AssumeRole → cdk-*-deploy-role, cdk-*-file-publishing-role,
                              cdk-*-image-publishing-role, cdk-*-lookup-role
              └─ CloudFormation deploys the stack
```

- The deploy role has **no direct permissions** on AWS resources. CDK's bootstrap roles do the work, and the CloudFormation execution role is the only role that changes resources.
- The deploy role can only assume roles with an `aws-cdk:bootstrap-role` tag, which bootstrap puts on the four roles above and not on the execution role.
- Trusting `environment:<env>` instead of `ref:refs/heads/main` means GitHub Environment protection rules (branch filters, and later manual approval for `prod`) also protect the AWS role.
- `OidcStack` is deployed once per account from a laptop with SSO credentials, because GitHub can't deploy until the role exists.
- `OidcStack` is in its own stage (`<env>-access/GithubOidc`). CI deploys `<env>/*`, so it never changes its own role.

| Risk                                                                                                                  | Mitigation                                                                                                                  |
| --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| The region-deny SCP blocks Bedrock cross-region inference, because `us.` and `global.` profiles route across regions. | Allow Bedrock inference outside `us-east-1` only through `us.` and `global.` profiles, and test with real calls in step 5.  |

  - S1-07 (fixed 2026-10-01): with the account ID fixed, AWS rejected the token (`Not authorized to perform sts:AssumeRoleWithWebIdentity`). GitHub uses immutable subject claims for repositories created after 2026-07-15, and this one was created on 2026-09-25. The `sub` is `repo:<owner>@<owner id>/<repo>@<repo id>:environment:<env>`, not `repo:<owner>/<repo>:environment:<env>` ([GitHub changelog](https://github.blog/changelog/2026-04-23-immutable-subject-claims-for-github-actions-oidc-tokens)). `GithubDeployRole` now trusts exactly that `sub`, built from the IDs in `infra/config/environments.ts`. The IDs are public, so they are committed. A renamed, transferred, or re-created repository gets new IDs and can't match, which is safer than the name-only form. Turning off immutable subjects for the repository was rejected for that reason. `<env>-access` was redeployed from a laptop in all three accounts.
  - S1-05: the baseline SCP also allows Bedrock inference through `global.` inference profiles, not only `us.`. The first version denied every `global.` call: Bedrock checks a region-less model ARN with `aws:RequestedRegion` = `unspecified`, which the Bedrock statement denied. That contradicted ADR-0002, which allows `global.` profiles, and blocked models that are `global.`-only in `us-east-1` (for example Sonnet 5.5 at the time). The exemption is by profile ARN, so `unspecified` is not allowed for other services, and every call must still start in `us-east-1`. ADR-0002 is amended: `global.` may be used for any task, and data residency is accepted as not a requirement at this stage.
  - S1-04: MFA is context-aware instead of asked at every sign-in, because there is one owner. ADR-0004 §3 records this and switches to always-on when a second person joins.
  - S1-04: the IAM user was deleted, not kept as a console fallback. Break-glass access is the management root user (MFA) and `sts:AssumeRoot`, so ADR-0004 needs no exception.
  - S1-04: access is assigned to a group, not to the user, so adding or removing a person is one membership change.
  - S1-06: account IDs are not committed, because the repository is public. The config reads them from `CVT_DEV_ACCOUNT_ID`, `CVT_STAG_ACCOUNT_ID`, and `CVT_PROD_ACCOUNT_ID`, set in the shell or in a gitignored `infra/.env` (template: `infra/.env.example`). A missing or malformed ID stops synthesis, instead of falling back to an account-agnostic stack that would deploy to whichever account the current credentials belong to. ADR-0004 §2 records this.

The CDK CLI refuses to deploy a stack whose account doesn't match the credentials, so placeholder mode can't deploy.   - S1-06: stacks now live inside Stages, so the CDK CLI needs a `'**'` selector (`cdk synth '**'`, `cdk deploy 'dev/*'`); without one it only looks at top-level stacks.

  - S1-07: the deploy role may assume `cdk-*` roles only when they carry the `aws-cdk:bootstrap-role` tag (`deploy`, `file-publishing`, `image-publishing`, `lookup`). Bootstrap v32 doesn't tag the CloudFormation execution role, so the role can't assume it. `image-publishing` is included for the AgentCore container images that come later. ADR-0004 §4 records this.

  - S1-07: tests create the app with the `cdk.json` feature flags and CDK metadata (`infra/test/test-app.ts`), so they check the same templates `cdk synth` produces. A bare `new App()` had neither, so ARNs came out as `Fn::Join` with `AWS::Partition`, and the hello stack's empty `Resources` section was never validated.
  - S1-08: `ci.yml` starts `deploy.yml` through `workflow_call` (`needs: check`), not through a `workflow_run` trigger. One run holds both jobs, the deploy uses the commit that was checked, and the workflow file comes from that commit. A `workflow_run` workflow always runs the default branch's file, needs an explicit checkout of the tested commit, and can't be exercised in a PR.
  - S1-08: the account IDs are Environment **secrets**, not variables, and there is no role ARN variable. The repository is public, so Actions logs are public. GitHub masks secrets as `***` in every log line, including the ARNs that `cdk deploy` prints; it doesn't mask variables. AWS doesn't treat account IDs as secret, but masking them keeps ADR-0004 §2 (IDs are not published) true for CI logs. The role ARN is built from `CVT_DEV_ACCOUNT_ID` and the fixed role name `GithubDeployRole`, so there is one less value to keep in sync.

- **Lessons learned:**
  - A unit test checks the value we expect, not the value an external system sends. The S1-07 trust test passed for a `sub` that GitHub never sends, and S1-08 was recorded as done while every deploy on `main` had failed. An item that connects two systems (here GitHub Actions and AWS) closes only after a real run succeeds and its result is visible on the other side. After every merge, `gh run list --branch main --limit 1` must show the run green, including `deploy-dev`.
  - Merging a hand-applied change is not the same as applying it. The S1-05 policies were merged on 2026-09-29, but the S1-10 checks showed they were not yet in AWS: a Sydney call succeeded, and so did a `global.` call that the first policy would have denied. A hand-applied item now closes only after its live verify steps pass, and the result is recorded under "Done".
  - IAM Identity Center groups and permission sets can have the same name. A stray group named `ReadOnlyAccess` was created during assignment and given both permission sets. Checking assignments with `aws sso-admin list-account-assignments` found it.
  - CDK unit tests don't go through the CLI, so they don't get the `cdk.json` feature flags or the `CDKMetadata` resource unless the test's `App` is given them. Without them, a test can pass against a template that differs from the one that deploys.
  - Check the review against the backlog at close, not against PR descriptions. PR #20 said the review had an S1-11 "Done" entry; it never did, and neither did S1-01, S1-02, or S1-09. From now on, each item's PR adds its "Done" entry, and the close step lists any backlog ID without one.
  - A scope decision pulls in other decisions. S1-13 also settled the data store, the knowledge base store, the quota values, and the domain. Recording each in its own ADR kept every decision reviewable on its own, instead of burying it in the scope ADR.
  - The sprint finished in 3 days, not 7, with 14 items. Hand-applied AWS steps (S1-03 to S1-05, S1-07, S1-09) took the most time, and every one of them needed a live check before it could close.
